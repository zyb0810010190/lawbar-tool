# WI queue

Consumed by the loop in `docs/wi-loop.md`. One row per work item; the loop reads the first
`ready` row, writes its outcome back, and advances only on `CLEAN`.

**Status** (control state): `ready` · `in-progress` · `held` · `done`
**Outcome** (set when a tick finishes): `CLEAN` · `FINDINGS` · `DECISION` · `BLOCKED`
These are two different axes. An earlier draft merged them into one enum, which made
`in-progress` and `CLEAN` look like alternatives in the same lifecycle.

**Tier**: defined canonically in `docs/wi-loop.md`. T2 = touches a court-facing invariant.
**Depends**: every listed WI must have Outcome `CLEAN` before this row is selectable.
**Owner / Since**: set at claim. An `in-progress` row whose `Since` is older than 60 minutes
is stale and the next tick resets it to `ready`. A missing or unparseable `Since` on an
`in-progress` row is treated as stale — fail toward recovery, not toward a permanent lock.

### Ordering — corrected

An earlier draft said "WI-01 first, deliberately", on the grounds that stage 5 (two-sided
verification) has no seam in `case-box-persistence`. That reasoning was **wrong for half
the queue**.

Two-sided verification proves a regression test *fails against the pre-change code*. For a
function that does not exist yet — `verifyDocumentStore` is the one real example here —
every test fails against the baseline trivially, because the symbol is undefined. A compile
error is not evidence that a test has teeth.

So the seam is a prerequisite only for items that **change existing behaviour**:

- **WI-02 was genuinely greenfield** — `verifyDocumentStore` did not exist at HEAD, so no
  baseline run could call it.
- **WI-03 and WI-04 were misclassified as greenfield, and the classification was wrong.**
  WI-03 added a gate inside `openSqliteCaseBoxPersistence`, a function that already existed;
  a baseline run could have opened a corrupt database and observed the old behaviour. WI-04
  extends an existing restore drill. Both had a real two-sided test available and skipped it.
  WI-03 subsequently needed a second round to close three shipped defects. That is not proof
  the skip caused them — the round-2 findings came from review, not from a baseline run — but
  it is the reason the criterion is now stated as reachability at HEAD, not "only adds
  behaviour". See the canonical rule in `docs/wi-loop.md`.
- **WI-04, WI-05, WI-06 and WI-07 all change behaviour that already exists**, so stages 2
  and 5 are live gates for every one of them. But WI-01 does **not** unblock them all, and
  saying so would repeat the mistake above in the other direction. WI-01 builds a seam for
  `case-box-persistence` only. WI-06 is persistence and is covered. WI-04 and WI-07 are in
  `apps/lawbar-desktop`, whose sole seam (`LAWBAR_SCRIPT_DIR`) reaches 5 release-script
  files and nothing else; WI-05 straddles both. Their `Depends` columns are therefore left
  as they are rather than pointing at a seam that would not reach them.

  This briefly looked like a blocker: no seam in the desktop package means stage 5 is
  unsatisfiable, and unrunnable means BLOCKED, not waived. It was resolved rather than
  waived — see D-7. The desktop baseline is built as a real `git worktree` at HEAD instead
  of being simulated by an env var, so stage 5 is live for WI-04, WI-05 and WI-07 and none
  of them is blocked. WI-01 keeps its original persistence-only scope; widening it would
  have bought nothing here.

**Row order is queue-and-history order; the loop selects the first row currently marked
`ready`, whatever that row happens to be.** An earlier draft
recommended starting there in prose while leaving WI-01 at the top — a recommendation the
loop algorithm could never honour. Row order IS the priority; there is no separate priority
field. WI-02 is first because it is the item where the product's central claim is currently
false: the audit chain is tamper-evident while the exhibits it points at are never re-checked.

WI-05 and WI-06 carry `Depends: WI-01` and stay `ready`. An earlier draft marked them
`held`, which was incoherent: the loop selects only `ready` rows, so WI-01 reaching CLEAN
would never have promoted them and a human would have had to intervene — defeating the
point. **`Depends` gates selection; `held` is reserved for items waiting on a human
decision** (the section below). Both are **T2**: they touch the audit chain, and the
workflow puts that in T2 regardless of how small the diff is.
