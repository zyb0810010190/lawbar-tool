## WI-601: docket-entry create + confirm IPC channels (deadline write path)
Type: IMPL
Scope: add two tenant-scoped write IPC channels + main-process handlers — one creates a PROPOSED CaseBoxDocketEntry via persistence.appendDocketEntry, the other confirms it via persistence.confirmDocketEntry which materializes the CaseBoxDeadline (the v1 deadlines/to-dos path per brief §7/§10) — enforcing the deadline/fact read handlers' matter-existence + active-tenant checks before each write; CRITICAL for confirm: because persistence.confirmDocketEntry(entryId, opts) takes NO tenant/matter parameter and does NOT itself scope the entry, the confirm handler MUST first verify the entry_id belongs to the requested matter AND active tenant via a scoped getDocketEntry({tenant_id, matter_id, entry_id}) preflight and reject (unknown_docket_entry / tenant_mismatch) before calling confirmDocketEntry — otherwise a guessed foreign entry_id could be confirmed cross-matter/cross-tenant; validate the renderer DTO and project each response through an ALLOWLISTED renderer-safe shape (the read handlers' projection approach, NOT registerDocumentHandler's raw persistence-row return); register the channels in caseBoxHandlers and wire them in electron main; do NOT touch any renderer path
Source of truth: docs/product/project-requirements-brief.md §7/§10 (READY); services/case-box-persistence/src/types.ts (appendDocketEntry proposed-only + confirmDocketEntry returns {entry, deadline}); apps/lawbar-desktop/src/caseBox/deadlineHandlers.ts (read/tenant/projection pattern) + documentHandlers.ts (write-validation pattern)
Allowed files: apps/lawbar-desktop/src/caseBox/docketHandlers.ts, apps/lawbar-desktop/src/caseBox/handlerShared.ts, apps/lawbar-desktop/src/caseBox/dto.ts, apps/lawbar-desktop/electron/ipc/caseBoxHandlers.ts, apps/lawbar-desktop/electron/main.ts, apps/lawbar-desktop/tests/ipc-handlers.unit.test.mjs, apps/lawbar-desktop/tests/dto-contract.test.mjs
Forbidden files: none
Gates: npm --prefix apps/lawbar-desktop test
Acceptance criteria: the docket-create handler creates a PROPOSED entry for a valid matter and RETURNS the allowlisted-projected entry in its response, and that proposed entry is NOT in the existing listDeadlines read path (no docket-LIST IPC is added — listDeadlines is the desktop read path used as proof); the docket-confirm handler, after verifying the entry_id belongs to the requested matter + active tenant, confirms a proposed entry and the resulting CaseBoxDeadline then appears in the existing listDeadlines read path; confirm REJECTS an entry_id that is unknown (unknown_docket_entry), that belongs to a DIFFERENT matter (rejected, not confirmed), or to a DIFFERENT tenant (tenant_mismatch) — covered by explicit tests; an unknown matter returns unknown_matter; a wrong-tenant matter returns tenant_mismatch; an invalid payload returns invalid_payload; the projected responses exclude server-authority fields; no renderer file is modified; the full apps/lawbar-desktop test suite passes

Depends on: none
Commit boundary: one local commit for the docket create + confirm IPC channels + handlers + DTO + tests
