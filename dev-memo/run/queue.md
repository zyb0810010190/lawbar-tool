## WI-CI1: contract-integrity guard + standalone checker (commit-boundary corruption defense)
Type: SCAFFOLD
Scope: Add a STRICTLY ADDITIVE commit-boundary defense against silent corruption of always-loaded contract docs (AGENTS.md, CLAUDE.md, GEMINI.md, .claude/rules/*.md). v1 corruption markers (contract-doc scope ONLY): numeric HTML entities matching `&#x[0-9A-Fa-f]+;`, stray `****` (literal four asterisks), prose backslash-escaped underscore `\_`. (1) New PreToolUse Bash guard `.claude/hooks/block-contract-corruption.sh` (mirror the deny() JSON shape + $CMD parsing of the existing Bash guards; READ-ONLY reference them, do NOT edit). SCOPE + THREAT MODEL (honest boundaries): this guard is ONE DEFENSE-IN-DEPTH layer, not a comprehensive cryptographic commit boundary. It covers the literal `git add` / `git commit` PORCELAIN surface — which is exactly what the autonomous pipeline uses (`git add <explicit-path>` + `git commit -m`) and what normal human porcelain use looks like. It does NOT, and does not claim to, intercept: git PLUMBING that writes commits/objects directly (`git commit-tree` + `git update-ref`, `git hash-object` + `git update-index`), shell ALIASES or `git -c alias.*=...` indirection, or any non-`git`/non-literal mechanism — a command-string PreToolUse hook cannot reach those. Those residual surfaces are covered by the COMPLEMENTARY layers: the standalone `scripts/workflow/check-contract-integrity.sh` (runnable as a pre-push / CI gate, independent of command parsing) and human/cc-suite review. The guard parses the literal command; if it is not a recognizable `git add`/`git commit` porcelain invocation, the guard takes no action (the complementary layers apply). GUARD INVARIANT (within the porcelain surface, enumeration-free): a recognized `git commit`/`git add` is DENIED whenever a contract doc that the command COULD stage or commit contains a v1 marker. The guard determines the "could stage/commit" set per the rules below, and where it recognizes a porcelain add/commit but CANNOT precisely resolve that set it FAILS CLOSED (the catch-all). The per-mode rules are how the set is computed; the catch-all closes any recognized porcelain add/commit mode it cannot resolve (incl. future flags) — it does NOT claim to close plumbing/alias surfaces (see SCOPE above). Per-mode resolution: (a) COMMIT, no pathspec, non-interactive (incl. `--amend`, multi-file; regardless of how staging happened — prior `git add`/`git add -u`/`git update-index`) — enumerate STAGED contract docs via `git diff --cached --name-only -- AGENTS.md CLAUDE.md GEMINI.md .claude/rules/*.md` and inspect each STAGED blob via `git show :<path>`; (b) COMMIT `-a`/`--all` — also inspect WORKING-TREE content of every tracked+modified contract doc (since `-a` stages it at commit time, not yet in the index); (c) COMMIT with INLINE PATHSPEC or `--only`/`-o` — `git commit <pathspec>` and `--only` commit ONLY the named paths' WORKING-TREE content, IGNORING the rest of the staged index; resolve the pathspecs (file/dir/glob/multi-arg) against the contract-doc set and inspect WORKING-TREE content of any would-commit contract doc; (c3) COMMIT `--include`/`-i` — UNLIKE `--only`, `--include` commits the EXISTING STAGED INDEX **plus** the named paths, so a corrupted contract doc already in the index would ride along; the guard must inspect BOTH (i) all STAGED contract-doc blobs via the staged-index net of mechanism (a) AND (ii) WORKING-TREE content of any included-pathspec contract-doc match (and, if `--include` is combined with `--pathspec-from-file`, apply the same staged-plus-included rule); deny on a marker in either set; (c2) COMMIT or ADD `--pathspec-from-file=<f>` (incl. `--pathspec-file-nul` NUL mode) — READ the pathspec file, resolve its entries against the contract-doc set, inspect WORKING-TREE content of matches; for `--pathspec-from-file -` (stdin, unreadable from the hook) apply the catch-all; (d) ADD with inline pathspec — resolve named/dir/glob/multi-arg pathspecs against the contract-doc set and inspect those contract docs' working-tree content; un-named staging (`git add -u`/`--update`, `git update-index`) is intentionally NOT caught at add-time and is instead caught at COMMIT via (a). CATCH-ALL (FAIL-CLOSED) — for any RECOGNIZED porcelain `git commit`/`git add` invocation the guard cannot precisely resolve to an exact would-stage/would-commit set, specifically the INTERACTIVE/selective modes `git commit -p`/`--patch`/`--interactive` and `git add -p`/`--patch`/`-i`/`--interactive`/`-e`/`--edit`, and `--pathspec-from-file -` (stdin), the guard treats the union of ALL staged contract docs AND ALL tracked-modified contract docs as in-scope and DENIES if any contains a marker (conservative; these modes require a TTY and are never used by the autonomous pipeline, which only ever runs `git add <explicit-path>` + `git commit -m`, so this never blocks normal automated commits). The catch-all is scoped to recognized porcelain add/commit modes ONLY — a non-porcelain or non-`git`-literal command is out of the guard's surface per SCOPE above (the complementary checker/review layers cover it). OVER-DENY AVOIDANCE (applies to the PRECISELY-resolved modes a/b/c/c2/d only): the guard fires ONLY when a contract doc is actually in the resolved staged/would-stage/would-commit set; a commit or add of unrelated NON-contract files in those modes MUST pass even if an unstaged contract doc is dirty/corrupted. The catch-all's conservative denial is accepted ONLY for the indeterminate interactive/stdin modes. It MUST NOT mutate files, MUST NOT run any markdown formatter, MUST fail CLOSED (deny) on inspection error, and MUST be additive (does not modify, reorder, or weaken the existing five guards; it is framed as an ADDITIONAL deny, not the sole commit boundary). (2) New `scripts/workflow/check-contract-integrity.sh`: greps the four contract-doc path globs for the three markers; exits 0 clean, nonzero (listing offending file+marker) when present; must NOT mutate the real AGENTS.md and must be testable against a synthetic corrupted temp copy/fixture. (3) Wire the new guard into `.claude/settings.json` by APPENDING it to the EXISTING PreToolUse Bash hooks array (after batch-commit-guard.sh) — hooks key ONLY; before staging run `git diff --cached .claude/settings.json` and confirm the diff is confined to the new hook entry (no permissions/plugins/theme/model/personal-key change). Do NOT edit any existing `.claude/hooks/*.sh`, any contract doc, or any product/source file. If closing the guard would require touching an existing guard or a contract doc, STOP and report.
Source of truth: dev-memo/plan-batch-workflow-contract-integrity-guard-00.md (discovery); the existing PreToolUse Bash guards `.claude/hooks/block-git-add-all.sh` / `.claude/hooks/block-commit-stage-all.sh` / `.claude/hooks/batch-commit-guard.sh` (deny() JSON + $CMD-parsing patterns to mirror — READ-ONLY, do NOT edit); `.claude/settings.json` PreToolUse Bash array (insertion target); the validated marker set (`&#x[0-9A-Fa-f]+;`, `****`, `\_`) which occurs 0 times across all current contract docs
