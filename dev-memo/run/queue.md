## WI-A3-UNLINK-00: unlink/break-link workflow design (design-only; NOT A0.7-gated)
Type: PLAN
A0.7-classification: A3-UNLINK-00 is design-only and intentionally NOT A0.7-gated. This docs-only ADR/plan SPECIFIES the explicit unlink/break-link workflow (how a link is intentionally detached from an anchor without deleting the anchor) BEFORE any unlink behavior is implemented; it implements no unlink code, no schema/migration, no delete, no UI, and changes no gate/marker behavior, so it needs no live provenance-valid A0.7 marker. Therefore this WI carries NO `Requires-A07:` line. ANY FUTURE unlink implementation MUST declare `Requires-A07: yes` (custody mode 9b). review-plan must confirm this classification; if review-plan says this docs-only WI must be A0.7-gated, STOP and report.
Scope: Define the explicit unlink/break-link workflow for A3 links as an ADR + a dev-memo sequencing plan, BEFORE any unlink behavior, preserving citation trust (unlink is NEVER an implicit cascade) and deciding how a link is intentionally detached from an anchor without deleting the anchor. Design/ADR ONLY — no code, no schema/migration change, no unlink/delete implementation, no resolver/export/delete-guard change, no UI, no dependency, no marker/key/gate change. Output: docs/adr/ADR-evidence-a3-unlink-break-link-workflow.md (A3-UNLINK-00) + dev-memo/plan-batch-casebox-evidence-a3-unlink-workflow-00.md; an optional additive cross-reference to the A3 cascade/resolver/export ADRs only if review-plan recommends it.
Default policy direction (record + justify in the ADR): unlink/break-link is a SEPARATE explicit operation (never triggered implicitly by anchor delete; A3-CASCADE-00 §4). It MUST NOT physically delete anchors, evidence/page/geometry records. An unlinked link MUST export as a DEGRADED (non-clean) state, preserving best-effort link/source identity. KEY M0 CONSTRAINT (verified against V11): case_box_links.anchor_id is NOT NULL and status CHECK is valid|needs_review|broken (no `unlinked`), AND the resolver (resolveLinkStatuses) recomputes status purely from anchor+page+geometry+supersession (ELSE 'valid') and buildExportCitations runs it FIRST — so a status-only 'broken' unlink on a link whose anchor is still structurally valid would be REVALIDATED back to 'valid'. Therefore a durable, link-PRESERVING explicit unlink is NOT M0-implementable without a schema decision; the ADR records this and gates the first implementation on it. Do NOT design an implementation that nulls anchor_id or adds an 'unlinked' status without a schema WI.
Required decisions to record (the 8 ADR questions): (1) OPERATION SEMANTICS — is unlink a status-transition-only or does it require schema change? Record the finding: a status-only unlink to 'broken' is NON-DURABLE (the resolver revalidates it to 'valid' on the next resolve/export), so a DURABLE link-preserving unlink REQUIRES either a schema change (a durable unlink reason/flag column, OR an 'unlinked' LinkStatus value + resolver awareness, OR a nullable anchor_id) — a future schema WI — OR a non-schema mechanism (physically removing the link row, which does NOT preserve the link row, conflicting with decision 3). Present the trade-off; recommend the link-preserving durable form (schema WI predecessor) and record the alternative; do NOT pick a schema design here. (2) ANCHOR PRESERVATION — the anchor row MUST remain on unlink (deletion is the separate, deferred unreferenced-delete WI / product decision; A3-CASCADE-00 §3). (3) LINK PRESERVATION — the link row SHOULD remain for audit/history unless a future reviewed policy says otherwise; note this is what forces decision 1's durable-state requirement (a preserved link with a still-valid anchor is the case the resolver revalidates). (4) EXPORT EFFECT — an unlinked/broken link MUST export as DEGRADED (non-clean), preserving best-effort link/source identity (A3-EXPORT-00 A10 no-drop; never a clean citation). (5) RESOLVER INTERACTION — DECIDE whether the resolver may overwrite an explicit unlink/broken back to 'valid'. Record that with TODAY's resolver it WOULD (status computed from structural inputs only), so the unlink implementation needs a DURABLE reason/source the resolver respects BEFORE code — this is the load-bearing reason decision 1 gates on a schema/mechanism decision. (6) AUDIT — DECIDE whether unlink emits audit events; an explicit unlink is a destructive-intent operation, so the future unlink IMPL MUST make audit semantics a PREDECESSOR/acceptance item (a destructive op must not ship unaudited; A3-CASCADE-00 §7); if the audit-event shape is unclear, DEFER + record (do not invent a shape). (7) SCHEMA — add NO schema in this lane; if a durable unlink reason/status is required (decision 1/5), RECORD it as a future schema WI (its own migration + ADR), not decided here. (8) A0.7 — this design-only WI is NOT A0.7-gated; ANY future unlink implementation MUST declare Requires-A07: yes (custody 9b).
