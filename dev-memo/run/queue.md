## WI-V1: audit-event-kind v2 canonicalization (contract + hash boundary)
Type: SOURCE
Scope: Implement the accepted ADR docs/adr/audit-event-kind-preservation.md at the contract/hash boundary. HIGH-RISK (public audit-event schema + hash chain on the security boundary) → security-WI loop (tests-first where practical). (1) Schema docs/contracts/case-box-contract/schemas/case-box-audit-event.schema.json: add an OPTIONAL `event_kind` (enum = the keys of CASE_BOX_AUDIT_EVENT_KINDS) and an OPTIONAL `audit_schema_version` (const 2 / integer); enforce the field-pair via `dependentRequired` (event_kind requires audit_schema_version and vice-versa, so both-or-neither; partial presence rejected); keep `additionalProperties:false`. (2) Regenerate docs/contracts/case-box-contract/src/generated/case-box-audit-event.ts via the project command `npm run gen:types` (do NOT hand-edit generated output except as the generator requires). (3) buildCaseBoxAuditEvent (audit-log.ts ~223-264): for new events set `event_kind = input.kind` and `audit_schema_version = 2`; preserve the existing action/entity_type derivation from CASE_BOX_AUDIT_EVENT_KINDS. (4) Consistency invariant — ENFORCE IT INSIDE verifyAuditChain's per-event loop in audit-log.ts (which already has CASE_BOX_AUDIT_EVENT_KINDS in lexical scope — NO new import, NO circular dependency), NOT only in buildCaseBoxAuditEvent: after validateAuditEvent succeeds and BEFORE the event is hashed (eventHashFn), if the event carries an `event_kind` its DECLARED CASE_BOX_AUDIT_EVENT_KINDS metadata MUST be consistent with the event per the ADR §4 invariant {action, entity_type, reasonRequired}: (a) meta.action === event.action AND meta.entity_type === event.entity_type, AND (b) if meta.reasonRequired is true then the event MUST carry a non-empty string `reason` — this kind-level reasonRequired is STRONGER than the JSON Schema's reason rule (which requires reason only for action === "privilege-waive", whereas many reasonRequired kinds map to other actions, e.g. DEADLINE_MISSED_TO_MET, FACT_REJECTED, *_REVOKED). On ANY mismatch (action/entity_type differ, OR reasonRequired kind with missing/empty reason) verifyAuditChain returns a failure (a new errorReason, e.g. `event_kind_inconsistent`). So a raw/imported/TAMPERED v2 payload whose event_kind disagrees with its action/entity_type OR omits a required reason fails verifyAuditChain — not just the builder. The enforceable invariant is "the kind's DECLARED {action, entity_type, reasonRequired} is consistent with the event" — the kind→{action,entity_type} map is MANY-TO-ONE, so this is NOT a uniqueness claim and tests must not imply uniqueness. Do NOT relocate this into validateAuditEvent.ts: audit-log.ts imports validateAuditEvent, so importing the kinds map there would risk a circular dependency; verifyAuditChain is the verification (security) boundary that always runs on every loaded/imported event, which satisfies the "not builder-only" requirement. (This cross-field rule is not expressible in plain JSON Schema; the builder path stays automatically consistent because action/entity_type derive from the kind.) (5) Branch canonicalAuditEventHashInput (audit-log.ts ~177-198): it MUST accept ONLY a valid v1 event (NEITHER audit_schema_version NOR event_kind present) OR a valid v2 event (audit_schema_version === 2 AND event_kind is a known CASE_BOX_AUDIT_EVENT_KINDS key) and THROW on anything else (a partial pair, audit_schema_version other than 2, or an unknown event_kind) — because eventHashFn/verifyAuditChain call canonicalAuditEventHashInput DIRECTLY, this defensive validation at the canonicalizer is a security-boundary requirement, not merely defensive. The v1 path MUST return the EXACT current 12-field canonical string byte-for-byte for legacy events; the v2 path includes the existing 12 fields PLUS `audit_schema_version` and `event_kind` in the contract's canonical (alphabetical) key order — i.e. action, actor_user_id, after_state_hash, audit_schema_version, before_state_hash, entity_id, entity_type, event_kind, id, matter_id, prev_event_hash, reason, tenant_id, timestamp. Because verifyAuditChain + persistence eventHashFn both call canonicalAuditEventHashInput, mixed v1/v2 chains verify with NO change to verifyAuditChain's chain-LINKING/hash logic (the only verifyAuditChain edit is the added post-validation consistency check of item (4)) and NO persistence change. (6) Register the new test file: append `tests/audit-event-kind-v2.test.mjs` to the `scripts.test` explicit file list in docs/contracts/case-box-contract/package.json — this ONE line only; change NO dependency/devDependency/version/engines/name/type/other-script and reformat nothing else (the contract test script is an explicit list, not a glob, so an unregistered test file would never run). Do NOT edit validators.test.mjs (it is over the LOC threshold and its v1 golden test must stay untouched as proof v1 is byte-identical). If closing this WI appears to require an SQL migration, a SQLite/persistence change, an apps/renderer/Electron change, a dependency change, or editing validators.test.mjs, STOP and report.
