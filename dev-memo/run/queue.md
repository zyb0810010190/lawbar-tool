## WI-AK1: ADR — preserve audit event kind as tamper-evident (versioned canonicalization)
Type: ASSET
Scope: Author ONE Architecture Decision Record at docs/adr/audit-event-kind-preservation.md. ADR + governance only — NO schema/contract/persistence/IPC/DTO/renderer/test/source change in this batch. The ADR records the REVISED decision (after broker review-plan review-plan-mq4v6gfn-cdy5f7 returned FAIL/BLOCK) to treat event_kind as AUDIT-SEMANTIC data, not display-only metadata: persist a normalized optional `event_kind` (the existing CASE_BOX_AUDIT_EVENT_KINDS key, e.g. DEADLINE_MET) and INCLUDE it in the canonical audit hash input for NEW-format events via VERSIONED canonicalization, so the met/missed/withdrawn distinction (which collapses to the same persisted {action:"update",entity_type:"deadline"}) becomes tamper-evident. The ADR must contain these sections: (1) Context + the integrity problem — audit panel renders raw action·entity_type; buildCaseBoxAuditEvent drops kind (audit-log.ts:223-264); DEADLINE_MET/MISSED/WITHDRAWN collapse to identical persisted {action,entity_type}; an UNHASHED event_kind is rejected because a direct DB edit DEADLINE_MET→DEADLINE_MISSED preserves the old 12 hashed fields and passes verifyAuditChain while flipping the rendered legal meaning. (2) Decision — persist normalized event_kind; include it in the canonical hash for new-format events; use versioned canonicalization rather than mutating the old format in place; legacy events verify under the old canonicalization, new events under the new; mixed old/new chains must verify; legacy rows display fallback action·entity_type; no backfill; no SQLite indexed column in the first path. (3) Versioned canonicalization design — define exactly how OLD events are hashed (the existing 12-field canonicalAuditEventHashInput, byte-identical, golden test unchanged) and how NEW events are hashed (12 fields + event_kind, plus any version marker); define how verifyAuditChain CHOOSES the canonicalization version per event; evaluate the selection mechanism options (explicit stored `audit_schema_version` field, vs derived-from-presence-of-event_kind, vs a contract version constant) and recommend ONE, explicitly analyzing whether the version field itself must also be included in the hash to prevent version-downgrade tampering. (4) Consistency invariant — event_kind MUST match its canonical {action, entity_type, reasonRequired} metadata from CASE_BOX_AUDIT_EVENT_KINDS; reject incoherent combinations (e.g. event_kind:DEADLINE_MET with entity_type:document); enforced at build-time and validated in tests; note this invariant alone does NOT make met/missed tamper-evident (same action/entity_type) which is WHY hashing event_kind is required. (5) Contract/schema implications — implementation must add an optional event_kind enum to case-box-audit-event.schema.json, regenerate the generated type, and because additionalProperties:false the schema must be updated before emission (contract-first ordering). (6) Persistence implications — event_json carries event_kind so no DDL/migration is required for the first path (listAuditEventsSqlite parses event_json at auditRepoQueries.ts:101 with no read-time re-validation); no SQL filter/index in the first path; a dedicated indexed column is deferred and separately governed. (7) Backward compatibility — existing rows have no event_kind and must continue to verify under the old canonicalization; collided legacy deadline rows cannot be reconstructed/backfilled honestly; renderer fallback remains action·entity_type for legacy rows. (8) Renderer implications — future UI maps event_kind to humanized labels with action·entity_type fallback for null/unknown; label-mapping design artifact required for that renderer work. (9) Alternatives rejected — unhashed event_kind (audit meaning is tamper-editable while verification passes); renderer-only derivation (deadline transition kinds indistinguishable after persistence); persisting an English display_label (bakes presentation into the audit record and still needs integrity handling); adding a SQLite indexed column now (deferred unless filtering/search later requires it). (10) Test plan for later implementation — golden OLD-format canonical hash remains unchanged; NEW-format canonical hash includes event_kind; tampering event_kind on a new event breaks verification; an event_kind inconsistent with action/entity_type breaks validation or verification; mixed old/new chains verify; legacy null-kind rows render fallback; new kinded rows render humanized labels in the later UI batch. (11) Hard stops — mutating the OLD hash format in place (must be versioned); fabricating backfill for legacy collided events; adding a SQL column/index without separate governance; implementing before ADR acceptance.
