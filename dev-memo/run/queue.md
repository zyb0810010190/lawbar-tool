## WI-A3-UNLINK-SCHEMA-00: durable-unlink schema mechanism design (design-only; NOT A0.7-gated)
Type: PLAN
A0.7-classification: A3-UNLINK-SCHEMA-00 is design-only and intentionally NOT A0.7-gated. This docs-only ADR/plan DECIDES the durable-unlink schema MECHANISM (how an explicit unlink is durably represented so the resolver/export can distinguish it from structural `broken`) BEFORE any schema implementation; it implements no schema/migration code, no DDL, no resolver/export change, and changes no gate/marker behavior, so it needs no live provenance-valid A0.7 marker. Therefore this WI carries NO `Requires-A07:` line. The FUTURE schema IMPLEMENTATION WI (the V12 migration) MUST declare `Requires-A07: yes` (custody mode 9b). review-plan must confirm this classification; if review-plan says this docs-only WI must be A0.7-gated, STOP and report.
Scope: Decide the durable-unlink schema mechanism as an ADR + a dev-memo sequencing plan, resolving the A3-UNLINK-00 load-bearing finding (a durable, link-preserving explicit unlink is not implementable on V11 because anchor_id is NOT NULL, LinkStatus has no `unlinked`, and the resolver recomputes a status-only `broken` back to `valid`). Specify the chosen schema mechanism + its resolver/export implications, preserving link history + citation trust, so a future A0.7-gated schema IMPLEMENTATION WI (the V12 migration) can build it. Design/ADR ONLY — no schema/migration code, no DDL, no resolver/export/delete-guard change, no unlink/delete implementation, no UI, no dependency, no marker/key/gate change. Output: docs/adr/ADR-evidence-a3-durable-unlink-schema.md (A3-UNLINK-SCHEMA-00) + dev-memo/plan-batch-casebox-evidence-a3-unlink-schema-00.md; an optional additive cross-reference to the A3 unlink/cascade/resolver/export ADRs only if review-plan recommends it.
Options to evaluate (record the comparison in the ADR): (1) durable unlink reason/flag columns on case_box_links (e.g. unlink_status / unlink_reason / unlinked_at) preserving anchor_id + the link row; the resolver checks the durable marker and does NOT recompute to valid — DEFAULT RECOMMENDATION; (2) add `unlinked` to LinkStatus (extends the enum beyond valid|needs_review|broken; requires resolver/export/status-ladder updates); (3) make anchor_id nullable (represents a detached link directly; risk: loses the anchor reference unless separate historical anchor fields are added); (4) a separate link-lifecycle/status table (more extensible but larger); (5) another reviewed mechanism. Default recommendation to test with review-plan: prefer a durable unlink marker/reason on case_box_links while preserving anchor_id; do NOT make anchor_id nullable in M0 unless review-plan strongly prefers it; do NOT overload structural `broken` as explicit unlink; do NOT add `unlinked` to LinkStatus unless the resolver/export status model is intentionally expanded.
Required decisions to record: (1) CHOSEN MECHANISM — the durable-unlink schema mechanism (default: option 1 — unlink marker/reason columns on case_box_links preserving anchor_id), with the rejected alternatives + why. (2) anchor_id — whether it remains NOT NULL (default: yes, preserved). (3) LinkStatus — whether it remains valid|needs_review|broken (default: yes, unchanged; the durable unlink is a separate marker, not a status value). (4) RESOLVER TREATMENT — how the resolver treats an explicitly-unlinked link: it MUST check the durable marker and short-circuit (NOT recompute the structural ladder back to valid); record the precedence (explicit unlink is distinguishable from + takes precedence over a structural recompute). (5) EXPORT FLAGGING — how export flags an explicitly-unlinked link: a deterministic non-clean exportFlag (best-effort identity, never clean/silently-valid; A10 no-drop); record whether it reuses an existing flag or needs a new one (decided/refined in the impl WI). (6) AUDIT METADATA — whether unlink needs durable audit-metadata fields on case_box_links or whether audit stays separate (an audit-event/log concern); record the decision or defer to the impl WI (do not invent an audit shape). (7) MIGRATION VERSION TARGET — the future implementation's schema version target (likely V12) — RECORDED as the target for the future WI; this lane bumps NOTHING. (8) APP-LAYER INVARIANT CHANGES — the new app-layer invariants the mechanism introduces (e.g. unlink_reason required iff unlinked; unlinked is terminal-until-relink; mutual exclusion with a clean citation). (9) BACKWARD COMPATIBILITY — V11 -> V12 forward-only additive migration; existing V11 rows default to "not unlinked"; no rewrite of existing data; the additive DDL pattern (matches DDL_STATEMENTS_VN). (10) A0.7 — this design-only WI is NOT A0.7-gated; the future schema IMPLEMENTATION WI (V12 migration) MUST declare Requires-A07: yes (custody 9b).
Design constraints (record + honor in the ADR): explicit unlink MUST be durable; MUST NOT be silently recomputed to valid; MUST export degraded / non-clean; the link row remains (recommended path) unless a future reviewed policy chooses physical link delete; the anchor row remains; the existing resolver missing-anchor -> broken stays the structural/corruption safety net; explicit unlink MUST be distinguishable from missing-anchor broken; NO SQLite cascade; NO physical delete; NO production-evidence-ingestion change.
