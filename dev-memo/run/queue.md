## WI-702: Add/Confirm Deadline UI + renderer bridge
Type: UI
Design artifact: dev-memo/design/2026-06-05-casebox-deadline-create-confirm.md
Scope: add an in-section two-step "Add deadline" -> "Confirm deadline" control to the Deadlines disclosure of the matter view and wire the renderer IPC bridge for the already-merged casebox:docket:create + casebox:docket:confirm channels — the renderer forwards a narrow CreateDocketEntryDto (matterId, proposed_kind, proposed_due_at, proposed_due_at_timezone, optional proposed_owner_user_id) to propose, holds the returned proposed entry in ephemeral renderer state, and forwards ConfirmDocketEntryDto (matterId, entryId) to confirm, which materializes the deadline that joins the existing listDeadlines read path. Mirror the document-register renderAddControl pattern: propose control (kind input + datetime-local + timezone field + "Propose deadline" button + status), then a transient view-deadlines-proposed area with a "Confirm deadline" button; on propose ok show the proposed row, on confirm ok clear it and refresh the deadline list (re-run loadDeadlines so the urgency banner reflects the new deadline), on !ok render inline role="alert". Safe DOM only (el()/textContent, no innerHTML). DATETIME/TIMEZONE RULE (review Medium): the datetime-local input carries no zone, and a naive new Date(value).toISOString() encodes HOST-local time. For THIS slice the timezone is CONSTRAINED to the host IANA zone — the timezone field is pre-filled with Intl.DateTimeFormat().resolvedOptions().timeZone and is read-only/disabled. The datetime-local value is interpreted as host-local by Date, but a host-local wall time can be NONEXISTENT (spring-forward DST gap) or AMBIGUOUS (fall-back overlap), which Date silently normalizes — so the forwarded instant could not match the displayed wall-clock. Add a renderer helper that validates the conversion is UNAMBIGUOUS — it must reject BOTH DST anomalies (the round-trip check alone catches the GAP but NOT the OVERLAP, because an ambiguous fall-back time round-trips cleanly since Date silently picks one of two valid instants): (1) GAP / nonexistent (spring-forward): parse the datetime-local components, construct the Date, re-derive the host-local Y/M/D/H/M components from that Date (via Intl in the host zone), and if they do NOT EQUAL the input components, the wall time is nonexistent -> reject. (2) OVERLAP / ambiguous (fall-back): a wall time is ambiguous when MORE THAN ONE instant maps to the same host-zone Y/M/D/H/M. The detection MUST be TRANSITION-SIZE AGNOSTIC — do NOT assume a one-hour DST shift (zones such as Australia/Lord_Howe transition by 30 minutes, so a ±1h-only probe would miss a 30-minute overlap). The REQUIREMENT: forward proposed_due_at only when the host-local wall time is EXISTENT and UNIQUE in the host zone; reject a nonexistent (gap) or ambiguous (overlap) time. Implementation guidance (not a hard-coded window): detect overlap with a bounded MINUTE-granularity scan of nearby instants around the constructed Date (e.g. the surrounding ±N hours at one-minute steps, excluding the instant itself) and reject if ANY other instant re-derives to the same input host-local components; the round-trip mismatch in (1) catches the gap. The exact scan bound is an implementation detail for the WI's TDD; the plan fixes the requirement, not the constant. Only forward proposed_due_at = Date.toISOString() when the time is existent (round-trips) AND unique (no other nearby instant maps to the same host-local components). On either rejection render an inline role="alert" error and do NOT call createDocketEntry. proposed_due_at_timezone is the host zone. Arbitrary non-host IANA timezone entry (which would require a general tz-offset computation) is OUT OF SCOPE for this slice. Add the two preload invokes, the CaseBoxClient/CaseBoxApi methods + createCaseBoxApi wiring with RENDERER_CREATE_DOCKET_DTO_FIELDS + RENDERER_CONFIRM_DOCKET_DTO_FIELDS strip-allowlists in renderer/types.ts (parity-checked by renderer-dto-sync), and any view-deadlines-add-*/proposed-* CSS using design tokens. Do NOT change any backend handler, DTO contract, persistence, or error surface; do NOT add a docket-read IPC.
