(4) MISSING ANCHOR — if the anchor_id does not identify an anchor in the (tenant, matter) scope, the guard exhibits deterministic NOT-FOUND/refusal behavior with NO mutation: default THROW a typed CaseBoxPersistenceError (default code `invalid_argument` — the anchor_id does not identify a scoped anchor; review-plan may pin a different existing/dedicated code). (5) TENANT/MATTER SCOPE — the referenced-check is tenant/matter-scoped (case_box_links WHERE anchor_id = ? AND tenant_id = ? AND matter_id = ?), consistent with anchors being single-scope; a (hypothetical) link in a DIFFERENT tenant/matter does NOT block the scoped guard. RECORD this interpretation; if review-plan rules that anchor_id is globally scoped and a cross-scope link must block globally, STOP and report. (6) RACE-SAFE SHAPE — the guard's existence-check + reference-check run inside ONE write transaction (db.transaction(...).immediate() style, as the resolver uses) so the FUTURE check+delete path (a later WI) is race-safe (A3-CASCADE-00 §9); since THIS WI performs no delete, the transaction proves the guard boundary only. (7) NO MUTATION — the guard writes NOTHING (no delete, no link-status change, no audit event); idempotent (repeated calls yield the same outcome, no writes). (8) RESOLVER/EXPORT SAFETY — the existing missing-anchor -> broken (resolver) + deterministic BROKEN (export) behavior remains a corruption SAFETY NET; this WI MUST NOT rely on breaking anchors to enforce policy and MUST NOT change resolver/export code. (9) AUDIT — refusal-only / non-destructive: emit NO audit events (deferred); if review-plan says even a refusal must audit AND the shape is unclear, STOP and ask; destructive delete remains forbidden until the audit-event shape (or a reviewed deferral) is resolved.
