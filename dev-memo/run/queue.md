## WI-DPE1: ADR — docket proposal edit (semantics + contract decision)
Type: ASSET
Scope: Author ONE Architecture Decision Record at docs/adr/docket-proposal-edit.md. ADR + governance only — NO contract/persistence/IPC/renderer/test/source change in this batch. The ADR records the decisions for editing a PENDING docket proposal before confirmation: (1) Product semantics — only `proposed` docket entries are editable; `confirmed` and `dismissed` are terminal and immutable through this flow; editing is CONTENT-ONLY (not provenance-editing); confirm-after-edit confirms the current edited proposal, not the stale original. (2) Editable fields — proposed_kind, proposed_due_at, proposed_due_at_kind, proposed_due_at_timezone, proposed_owner_user_id, reminder_offsets. (3) Immutable provenance/lifecycle fields — source_type, extractor_name, extractor_version, extraction_confidence, source_document_id, source_page_number, source_excerpt, source_rule_citation, all identity fields (id/tenant_id/matter_id/actor_user_id), all lifecycle fields, and all confirmation/dismissal fields. (4) Audit strategy — add a new audit kind DOCKET_ENTRY_REVISED (action: update; entity_type: docket_entry; reasonRequired: false unless the ADR explicitly rejects that, with rationale); revision is tamper-evident via before_state_hash/after_state_hash (event_kind is hashed per the shipped v2 work); do NOT store full literal before/after values unless the ADR gives a specific reason. (5) Edited-state visibility — add an OPTIONAL `revised_at` field in the docket-entry payload (set on edit); the UI shows an "(edited)" marker/badge when present; preserve original source/provenance so the user can distinguish machine-suggested vs user-edited content. (6) Persistence stance — NO migration expected; edit updates payload_json in place and updates the lifted proposed_kind column only if proposed_kind changed; if a reviewer proves a new lifted/indexed column is needed, STOP and split into a separate migration WI. (7) Cross-package coupling — adding DOCKET_ENTRY_REVISED to the contract audit-kind enum requires the renderer audit label map (apps/lawbar-desktop/renderer/screens/auditEventLabels.ts) to gain "Docket proposal revised" so the contract<->label sync test stays green; the ADR MUST explicitly decide whether that ONE renderer-label line belongs in the contract WI (DPE2) or is deferred to the UI batch. (8) Hard stops — any confirmed/dismissed mutation; any provenance overwrite; any ambiguity in confirmation semantics; any migration requirement not separately governed; any expansion into reminders/scheduling/audit-filtering/event-kind UX polish/workflow Low cleanup. The ADR must cite the verified discovery facts (the docket-entry schema fields, confirmation_state transitions proposed->confirmed/dismissed, the three existing DOCKET_ENTRY_* audit kinds, the confirm-materializes-from-current-payload behaviour, the in-place updateDocketEntryRow pattern) and relate to docs/adr/case-box-step-6-deadline-docketing-rules.md + docs/adr/audit-event-kind-preservation.md. The ADR concludes with the proposed downstream WI breakdown (contract / persistence / IPC / UI) and the cc-suite review requirement. If authoring requires editing any contract/persistence/IPC/renderer/test/source file, STOP and report — this batch authors the ADR only.
