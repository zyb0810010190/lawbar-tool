## Audit history for this range — FAIL then PASS

**Round 1 (`audit-msmhjlfp-92ofxu`) = BATCH-FAIL C0 H1 M0 L0.** The H1: `block-run-control-bash-write.sh`
still had protected-file bypasses because the target-truncation set omitted `<` and `>` and quote handling
was a whole-string parity heuristic. Severity was real — every protected run-control file was reachable,
including `human.override`, so an agent could have written its own authorization.

**Round 2 (this attestation) = BATCH-PASS C0 H0 M0 L1.** The auditor confirmed `cut_meta()` is now applied
in the redirect path AND the verb/indirection paths, before and after quote stripping; that unbalanced
quoting now DENIES rather than passing through; and that it could find no remaining same-class bypass for
`< > ( ) ; | &`, whitespace, `>>`, `>|`, quoted segments, or unrelated apostrophes. Protected files were
EXTENDED (not reduced) — `remediation.authorized` added consistently across the Bash hook, the Write/Edit
guard, the canonical helper, and the tests.

**L1 — ACCEPTED, no code change.** `rem_tokenize()` in the remediation lane is intentionally restrictive
and treats `$` or a backtick inside a quoted commit message as a metacharacter, so a legitimate
remediation commit whose message contains `$` would be denied. Friction on a narrow escape path, not a
bypass and not a weakening. Recorded rather than fixed: loosening a tokenizer on the authorization path
is exactly the kind of change that should not be made casually. Workaround: pass the message via
`git commit -F <file>` (already the practice in this repo for messages containing shell-like text).

## What BRCBW-12 actually found (one of my premises was wrong)

- `<` glued to a redirect target: CONFIRMED bypass. **`>` glued was ALREADY denied** — a normalisation
  step rewrites `>` before tokenising, so my stated premise was incorrect. `(` was also live and unlisted.
- The verb-argument scan (`rm`/`cp`/`mv`/`tee`/`touch`/`sed -i`/`dd of=`) had NO normalisation at all, so
  both `<` and `>` bypassed there; also fixed in `ind_check` and the `cd` operand.
- `deobf()` stripped quotes only when whole-string quote counts were even — an unrelated apostrophe
  anywhere left the token unstripped, i.e. **fail-OPEN**.
- **Two further bypasses found by sweeping the same class, neither previously reported:** the `[[ ... ]]`
  blanking and the statement splitter are both quote-blind, so `rm 'a;b' <protected>` ended the statement
  early and the real target landed in a fragment whose first word was not a write verb.

Evidence: 56 new cases run against the PRE-change hook gave 233 passed / **42 failed, every failure in the
`want DENY got ALLOW` direction**, zero false-positive direction; after the fix 275/275. Non-weakening was
proved DIFFERENTIALLY over a generated 2250-command corpus: `same=1528, new-denials=722, WEAKENED=0`.

## Governance note — the remediation lane could not be used, and why

This commit was authorized by the GENERAL `human.override`, not the narrow lane built one commit earlier,
because **the lane is structurally unreachable under this config**: `AUTO_ADVANCE_MAX == BATCH_AUDIT_EVERY
== 3`, so audit-due and the breaker always trip on the same commit. The lane clears audit-due only; the
breaker denied anyway. The lane correctly evaluated the breaker BEFORE consuming the token, so the human's
token was preserved unspent.

Per the Codex consult `review-plan-msmmzplq-lr4udj`: applying the breaker to a human-created, single-use,
path-scoped remediation token is a **category error** — the breaker exists to stop long UNATTENDED runs,
and such a token IS human attendance. The deeper bug is that audit-due ("has this batch been reviewed?")
and the breaker ("has automation run too long without a human?") answer different questions from the same
counter with identical reset semantics. Raising `AUTO_ADVANCE_MAX` was rejected: it would pass this
instance by configuration accident, weaken the breaker globally, and leave the design broken.

**Follow-up WI (next):** make a valid remediation token count as human attendance for breaker purposes,
scoped to the same predicates (failed job id, output digest, declared paths, single use, no marker
advance, mandatory follow-up PASS). An invalid token or unrelated staged files must still hit the breaker.

## Standing posture carried forward

The relabel in `152bc66` is the more important half of that commit: the guard's header now states it is
**best-effort command hygiene, NOT an enforcement boundary** — it prevents mistakes, not forgery. The
documented remaining bypasses (`sh -c`, `eval`, computed/expanded paths, write-then-run, alias/function
indirection, interpreters that shell out) are a PERMANENT LIMITATION, not a backlog. Real trust must move
to CI and producer-bound attestation outside the agent's uid.
