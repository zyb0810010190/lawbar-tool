## Audit history for this range — two rounds, and why

**Round 1 (`audit-mslfl953-z4blf5`) returned BATCH-FAIL C0 H0 M1 L1** — a genuine defect in the
brand-new privacy gate, not a false positive. `collectPartyNameValues` evaluated a party field only when
`typeof value === "string"`, so a parseable-but-malformed fixture bypassed the allowlist entirely:
an object wrapper, an array wrapper, a number, or null all caused the walk to descend past the key and
emit NO hit. The gate failed closed on UNPARSEABLE json but passed parseable-malformed — contradicting
its own documented contract. Its tests covered the cases that already worked and not the one that did not.

**Remediation** (`34e9a56`): party-name fields are evaluated BY KEY regardless of value type; a
non-string label is itself invalid provenance and fails with a distinct `party-name-not-a-string` reason.
Recursion below the check stays unconditional, so nested labels inside a malformed wrapper keep coverage.
The offending value is deliberately NOT echoed — a wrapped value may be a real name and would otherwise
land in CI logs. L1's loose `示例` prefix was anchored to the single form the corpus actually contains.

**Red-before-green:** the 14 new tests ran against the UNMODIFIED script first — 47 tests, 37 pass,
10 fail, with all five malformed shapes returning zero hits. Post-fix 47/47. Live negative control fails
with exit 1 in the DEFAULT no-args mode (how `pretest` actually invokes it). Full suite 944/943, the sole
failure the accepted `smoke.electron.test.mjs:21` Electron timeout.

**Round 2 (this attestation) returned BATCH-PASS C0 H0 M0 L0.** The auditor confirmed M1 closed
(including that getter/prototype/container tricks create no evasion path under `JSON.parse`), L1 closed,
no weakening anywhere, and the failure message safe.

## Governance note — a structural flaw, now seen twice

Round 1's FAIL blocked ALL commits, including the one that would RESOLVE it. A Medium cannot be deferred
into a passing attestation (`batch-closeout.mjs` requires `BATCH-PASS C0 H0 M0`), so fix-and-re-audit is
the only path — and it needs a commit. The remediation therefore required a **single-use human override**,
consumed and logged. **This is the second occurrence** (batch-281 was the first, per the prior override
record). The policy says findings are "resolved as a new WI" while the guard forbids that WI's commit:
there is no remediation lane.

Per the Codex consult `review-plan-mslg8u2h-5x4ksy`, the minimal safe fix is a bounded remediation lane —
authorized by a non-agent-writable artifact naming the specific finding ID and allowed paths, which does
NOT advance the marker, and still requires a follow-up audit PASS. The agent may implement a fix but must
never authorize its own remediation. **Follow-up WORKFLOW WI; not done in this window.**

## Known limitation carried forward

The gate is DIFF-SCOPED: it checks fixtures a WI touches, so a dormant real name in an untouched fixture
is never re-checked. It catches new introductions, not existing data — so it does not by itself close the
scenario that produced `f86c8e4`. A full-scan variant (or a CI job) is the piece that would.
