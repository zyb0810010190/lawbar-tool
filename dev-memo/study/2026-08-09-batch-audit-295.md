## The spec correction inside 19be588 (worth preserving)

The WI as written required the ARTIFACT to carry `queue_sha256` equal to the current queue hash. That does
**not** achieve its own rationale: the artifact is agent-writable, so any past PASS job could be replayed
onto any future queue by writing today's hash locally. Only a digest inside the **hash-pinned broker
output** makes the transplant impossible. The implementer identified this and implemented both; a test
drives the full transplant scenario (v1 review vs edited v2 queue).

**Operational consequence:** the reviewer prompt must now emit both `QUEUE_REVIEW_VERDICT=PASS` and
`QUEUE_REVIEW_SHA256=$(shasum -a 256 dev-memo/run/queue.md)`. No existing review-plan job carries the
second line, so the next queue governance requires a FRESH review — a prior PASS cannot be reused.

## Residual carried forward — the whole broker-binding family shares it

**The cc-suite state store is agent-writable.** Nothing blocks writing a fabricated
`.../state/<slug>-*/jobs/<id>.json`; `.claude/settings.json` has no deny rule for that path and
`protect-run-control.sh` covers only `dev-memo/run/**`. This residual is IDENTICAL for
`batch-closeout.mjs`, the remediation lane, and now the queue-review leg. The honest description of all
three is **"cooperative-agent + hash-bound provenance", NOT cryptographic.** Closing it needs a separate
WI (a write-guard over the plugin state dir, or a signature the agent cannot mint) — and it is the third
independent confirmation of the decided strategy: real trust must move to CI / a producer boundary outside
the agent's uid.
